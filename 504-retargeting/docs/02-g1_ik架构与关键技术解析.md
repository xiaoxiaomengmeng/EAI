# g1_ik 架构与关键技术解析

> **证据等级**：实测背书型。所有机制描述均经源码核实（2026-10-20 六模块重构后状态），验证数据标注「实测」；live 模式与 wuji 解析解内部行为未实测，标注「待核」。
> 操作细节（滑杆表、标定步骤、场景用法）在 [g1_ik/README.md](../pico2g1/g1_ik/README.md)，本文只写原理与架构；部署实测（环境搭建、命令与判据）见 [01-pico2g1 部署复现实测记录](01-pico2g1部署复现实测记录.md)；当前状态见 [START_HERE.md](../START_HERE.md)。

## 1. 定位与总览

`pico2g1/g1_ik` 是三条重定向链路中**最轻**的一条：不跑策略网络，直接用 MuJoCo 雅可比 + 带限位最小二乘把 PICO 动捕（24 关节 + 左右手 tracker）和手套数据（21 关键点）映射成 G1 全身 29 DoF + Wuji Hand 40 关节。用途是验证「人体→机器人映射关系本身」、调身体比例差异，以及给另两条 SONIC 链路提供录制底座（录制功能由共享层提供）。

| 属性 | 值 |
|---|---|
| 控制频率 | 50 Hz（`FPS`，回放重采样与 live 节流共用） |
| 求解对象 | G1 本体 29 DoF（IK）+ Wuji Hand 左右各 20 关节（重定向） |
| qpos 布局 | 7 浮动基座 + 29 本体 + 40 手部 = 76（互动场景物体追加在后） |
| 算力 | 纯 CPU，不需要 GPU / torch（实测：RTX 5090 机器上未占卡） |
| 界面 | PySide6：MuJoCo 主画面 + 头部/双腕相机 + 2D 人体/双手线框 + 调参滑杆 |

端到端数据流（两个入口汇合同一条消费链）：

```
replay: session 四类 parquet ─┐
                              ├─> g1_recording 加载/过滤/重采样 50 Hz
live:   ws://设备:9990 ───────┘            │
                                           ▼
                              g1_source 帧生成（节拍/订阅/手套融合）
                                           │  LatestFrame 单槽总线（后台线程生产）
                                           ▼
                    Qt 50 Hz 定时器消费 → ik.solve(pose)   ← 29 DoF 身体
                                       → set_hands(hands)  ← 40 关节手部
                                           │
                                           ▼
                    g1_window：MuJoCo 渲染 / 2D 线框 / 录制 / 推流 / 标定调参
```

## 2. 架构

### 2.1 六模块平铺 + 瘦入口

2026-10-20 由 1407 行单文件重构而来：71 行瘦入口 + 6 个 `g1_` 前缀平铺模块（合计 1494 行），依赖**严格单向无循环**：

```
g1_config ← g1_recording ─┐
          ← g1_model ─────┼─← g1_ik ← g1_source ← g1_window ← launch_g1_ik.py
```

| 模块 | 行数 | 职责 |
|---|---|---|
| [g1_config.py](../pico2g1/g1_ik/g1_config.py) | 97 | 常量表：关节名/边/调参默认值/旋转任务表 + 资产与 wuji 路径；首次导入时把仓库根注入 `sys.path` |
| [g1_recording.py](../pico2g1/g1_ik/g1_recording.py) | 186 | parquet 加载与过滤、live 消息解析、slerp/重采样 |
| [g1_model.py](../pico2g1/g1_ik/g1_model.py) | 107 | `build_model`：G1 + Wuji Hand MJCF 拼装、场景注入 |
| [g1_ik.py](../pico2g1/g1_ik/g1_ik.py) | 302 | `FullBodyIK`（标定 + 求解）、`WujiMapper`、`set_hands` |
| [g1_source.py](../pico2g1/g1_ik/g1_source.py) | 136 | `replay_frames`/`live_frames` 帧生成、`load_tuning`、`LatestFrame` 帧总线 |
| [g1_window.py](../pico2g1/g1_ik/g1_window.py) | 595 | `SourceView`/`MuJoCoView`/`TuningWindow` 三个界面类 |
| [launch_g1_ik.py](../pico2g1/g1_ik/launch_g1_ik.py) | 71 | argparse（replay/live 子命令）+ `run`/`main` + re-export |

**为什么平铺不用子包**：入口被 `python launch_g1_ik.py` 直调、测试 `tests/test_scenes.py` 又用 `spec_from_file_location` 按文件路径加载，两种姿势下同目录平铺模块都能直接 `from g1_xxx import`；子包则两处都要改调用方式。**为什么带 `g1_` 前缀**：测试加载时 `sys.path` 同时含 g1_sonic 与 g1_ik 两目录，无前缀的 `config.py`/`model.py` 会与将来 sonic 侧拆分撞名。

### 2.2 三条结构性不变量（改代码前必读）

1. **路径推导集中在 g1_config.py**：`REPO_ROOT`/`G1_XML`/`WUJI_ROOT`/`TUNING_PATH` 全部基于 `__file__` 推导（可被 `G1_DESCRIPTION`/`WUJI_ROOT` 环境变量覆盖），且它首次 import 时把 `REPO_ROOT`（pico2g1/）插入 `sys.path`——后续 `from sim_scenes import ...` 依赖这一步，模块导入顺序不可调（入口 L11-13 注释即为此）。
2. **入口 re-export 三个名字不可删**：`__all__ = ["FullBodyIK", "TUNING_DEFAULTS", "build_model"]`。tests/test_scenes.py 按文件路径加载入口后直接取这三个符号，删掉 re-export 会**静默**打断测试。
3. **模块名 `g1_` 前缀防撞名**（见 2.1），sonic 侧将来拆分照此用 `sonic_` 前缀。

### 2.3 与 sim_scenes 共享层的关系

[sim_scenes/](../pico2g1/sim_scenes/) 是 g1_ik 与 g1_sonic 两条 GUI 链路的**薄共享层**（14 个 py 模块 + web/）：场景解析与互动场（`--scene empty|xixi|pulse|strike|orbit|switchyard`）、LeRobot 录制（`lerobot_recording.py` 状态机 + Qt 控件）、八路 MJPEG 推流、渲染视图（robot_cameras / mouse_view / viewport / shadows）。g1_ik 只 import 不复制；但 IK、数据加载等自身逻辑仍在自己目录——「三方法刻意自包含、勿跨方法抽公共代码」是既定设计（各自独立 .venv 也是同一逻辑）。g1_sonic_bridge 无界面，完全不碰这层。

### 2.4 线程模型与帧总线

生产者-消费者解耦：`publish_frames` 在 daemon 线程里跑帧生成器（replay 的节拍 sleep / live 的 WebSocket 收包），把每帧塞进 `LatestFrame` 单槽；Qt 主线程 `QTimer` 每 20 ms（1000/50）触发 `consume_frame` 取走消费。三个设计点：

- **丢帧语义**：`LatestFrame.take()` 取走即清空——UI/IK 跟不上时只保留最新帧，不堆积延迟（遥操作场景下正确取舍）。
- **单帧回滚**：消费时先 `previous_qpos = data.qpos.copy()`，`ik.solve`/`set_hands`/渲染链路中任一异常 → 停录制、恢复 qpos、`mj_forward`，状态栏报「本帧已回滚」，绝不让半解算状态污染下一帧。
- **错误终结**：生产者异常写入 `latest.error`（完整 traceback），消费侧置 `failed` 后停录制、停止解算，但场景仍可查看；数据流自然结束（replay 放完）则报「回放结束 · 最后 IK 残差」。

## 3. 关键技术

### 3.1 模型装配 build_model（g1_model.py）

G1 官方 MJCF（`assets/g1_description/g1_gear_wbc.xml`）在加载时做 XML 手术：

1. `meshdir` 重定向到本仓库网格；删除 `left_hand_*`/`right_hand_*` 原厂手部 mesh 资产。
2. 加载 Wuji Hand 左右 MJCF，mesh 路径改绝对，合并 asset。
3. 左右 `*_wrist_yaw_link` 下：删原手 body/geom → 装 docking adapter geom（`pos 0.0415`）→ 装 Wuji 手掌 body（`pos 0.066`），两者同用 `quat 0.7071 0 0.7071 0`（绕 y 轴 90°，wxyz）。
4. `add_robot_cameras` 挂头部/双腕三相机；`--scene xixi` 注入办公场景（mesh 绝对路径重写、删原 floor、**跳过场景自带 light**——不加过滤会和主光源叠加过曝）；互动场景追加可动物体。

最后 `MjModel.from_xml_string` 编译。**实测**：`build_model()` 输出 `nq=76`（robot 76，互动场景物体 DOF 追加在其后），与 3.8 的录制格式约定一致。

### 3.2 多流对齐与重采样（g1_recording.py）

输入契约：session 四类 parquet（`umi_multimodal_capture` schema v1.1.1）各流独立加载与过滤（实现在 g1_recording.py）：

| parquet | 内容 | 加载函数 | 过滤条件 |
|---|---|---|---|
| `observation.data.vr_full_body_*` | 24 关节 pos+quat（xyzw）、`available` 标志 | `load_recording` | available 且全部有限且四元数模长 > 1e-8 |
| `observation.data.vr_*` | 左右手 tracker `left/right_controller` | `load_hand_trackers` | 有限 + 四元数非零 |
| `observation.data.glove_left/right_*` | 21 关键点 `recv_timestamp_ns` + 校准态 | `load_glove_recording` | `calibration_state == 3`（已校准） |

三路数据频率不同（手套 ~90.9 Hz、VR 手部 ~76.6 Hz、live 推送 90 Hz），全部归到 50 Hz 主时间轴：

- **主轴重采样**：`resample` 以 `1e9/50 = 20 ms` 步长生成目标时间网格，`searchsorted` 找邻帧对，位置线性插值 + 旋转 **slerp**（手写实现：`dot < 0` 取负走短路径；`sin_theta ≤ 1e-6` 退化时回退线性插值后重新归一化）。
- **跨流对齐**：`resample_poses_to` / `resample_points` 把 tracker、手套插到主轴时间戳上——**按时间戳而非帧号**（复现红线，见 START_HERE）。
- **腕部旋转替换**：`apply_hand_trackers` 只把腕关节的**四元数**换成 tracker 的（位置仍用 24 关节数据），即腕部朝向以 VR controller 为准且不做 tracker→人体腕部的首帧对齐。
- **有效性口径**：所有流统一「时间戳严格递增 + 数值有限 + 四元数非零（手套另加校准态 == 3）」，过滤后不足 2 帧直接报错，绝不带病回放。

### 3.3 FullBodyIK 首帧标定（g1_ik.py）

`calibrate` 在第一帧完成三件事，之后所有帧的目标生成都建立在其上：

1. **方向基 `source_to_g1`**（3×3 旋转）：左右肩中点差与左右髋中点差取均值得人体左右向量，清掉竖直分量并归一化，与竖直轴 `up=(0,1,0)` 叉积出第二轴，堆叠成源（VR 世界）→ G1 的旋转基。人体朝向约定在此一次性定义。
2. **肢体比例 `scales`**：腿（hip→knee→ankle）、臂（shoulder→elbow→wrist）分别算「机器人三关节链长 / 人体链长」，左右取均值，`clip(0.6, 1.4)`——人体和机器人尺寸差异的缩放因子。
3. **旋转对齐表 `rotation_alignment`**：5 个旋转任务各记一个 3×3 补偿阵 `(source_to_g1 @ R_source_first)ᵀ @ R_robot_first`，语义是「人体 rest 姿态 → 机器人 rest 姿态」的残差（T-pose 与自然站姿差异等）。首帧求解（30 迭代）收敛后写入；之后每帧目标 = `source_to_g1 @ R_source @ alignment`。界面「重新标定身体」即清空 1/2/3 以当前锁定帧重算。

### 3.4 FullBodyIK 每帧求解

**目标生成 `targets`**：

- 根位姿：骨盆位置 = neutral 位置 + `leg_scale × scales.leg` × （方向基变换后的位移）；根旋转 = 躯干相对旋转（`R_now @ R_firstᵀ` 过方向基变换）。
- 8 个位置目标（左/右 × 膝/踝/肘/腕）：从根位姿变换出的肩/髋锚点（y 向可乘 `shoulder_width`/`hip_width` 微调）出发，加 `scales × limb_scale × 方向基变换后的源相对位移`——追踪的是**相对锚点的位移**而非绝对位置，标定比例直接生效。
- 5 个旋转目标（躯干/双腕/双踝，`ROTATION_TASKS` 表）：见 3.3；腕部额外可乘滑杆欧拉修正（`left_wrist_x/y/z`，度）。

**求解 `solve`**（每帧）：

- 误差向量：8 位置（各 3 维）+ 5 旋转（各 3 维 rotvec）= 39 维，逐任务乘 `tuning` 权重。
- 雅可比：`mj_jacBody` 取各任务 body 的雅可比、只留 29 个本体 DoF 列。
- **速度限位**：非首帧把 `lsq_linear` 的边界收紧到 `previous ± 6.0/50 = ±0.12 rad`——机器人物理上转不过来的动作直接被边界拦住，靠限位而非阻尼保安全。
- **DLS**：`lsq_linear([J; λI], [e; 0], bounds=(lower−q, upper−q))`，λ 即 `damping`（默认 0.04）——带边界阻尼最小二乘，天然处理限位；构造限位另有两处硬编码：膝下限 ≥ 0（防反关节）、肘上限 ≤ π/2。
- 迭代：首帧 30 次、后续 8 次，残差范数 < 0.01 提前停；首帧解完补记 `rotation_alignment`。**实测**（2026-10-20，六模块重构回归）：真实 session 首帧残差 0.0498 / 0.0503，连续 100 帧 solve 输出全 finite。

### 3.5 四元数顺序（复现红线）

parquet 与内部 pose 全程用 scipy 惯例 **xyzw**（`Rotation.from_quat`）；写 MuJoCo 时换序 **wxyz**：`data.qpos[3:7] = root_quat[[3, 0, 1, 2]]`（g1_ik.py L150）。3.1 的 adapter/palm `quat` 则直接是 MJCF 的 wxyz 字面量。两处顺序不一致是这类移植最高频的错误源。

### 3.6 手部重定向 WujiMapper / set_hands

- 手套侧不自己做 IK：加载 21 关键点（腕 + 每指 4 点 × 5 指，`GLOVE_JOINT_NAMES`），位置乘 `(-1, 1, 0..)` 中的 x 翻转 `(-1, 1, 1)`（手套坐标系与 wuji 期望镜像），交给 wuji-retargeting 的 `adaptive_analytical_wuji_glove_{side}.yaml` 解析解配置（**待核**：wuji 内部 FullHandVec 损失对 21 点的具体取用，见其配置 `thumb_skip_pip` 等）。
- `lp_filter.alpha` 接到滑杆 `hand_response`（默认 0.2）——低通系数即「手部响应速度」。
- 输出按 `WUJI_JOINTS`（`finger{1..5}_joint{1..4}`，每手 20 关节）顺序校验后逐关节 `clip` 到限位写 qpos；关节顺序不符直接抛错（防 wuji 版本变化静默错位）。

### 3.7 界面与调参闭环（g1_window.py）

三视图联动：左侧 MuJoCo 主画面（默认镜头 lookat [0.15, 0, 0.8]、distance 2.5、方位角 135°、俯仰 −15°）+ 头部/双腕三相机面板（录制画面源）+ 右侧 2D 线框（身体正视/侧视投影过 `source_to_g1` 基，所以看到的是「对齐后」的人体；标定时黄圈标 8 个位置目标、RGB 轴标旋转目标）。

调参闭环的设计：进入标定 → replay 置 `pause_event`（帧生成器挂起）/live 继续收包但画面锁定 → 之后每拖一个滑杆都用**同一帧**重新跑完整 `targets + solve`，参数效果立即可比 → 「保存并继续」写 `tuning.json`（本地不入库，下次启动 `load_tuning` 自动加载，非有限值/未知键静默忽略）。19 个滑杆分四组：身体比例 4、平滑与求解 2、IK 任务权重 7、手腕目标局部旋转 6——后两组的区分是「IK 追踪该朝向的权重」与「目标朝向的角度修正」。

### 3.8 录制链路与校验恢复

录制不在本目录实现，由共享层 [sim_scenes/lerobot_recording.py](../pico2g1/sim_scenes/lerobot_recording.py) 状态机承担，界面侧 `RecordingControls` 挂在 TuningWindow（`action_semantics` 写明：运动学 IK，state 等于源采样时刻的目标、导出 state 为插值、action 为保持——训练用数据集的语义声明）。

- **产物**：LeRobot v2.1 数据集——三路 1280×720 / 30 fps / H.264 + 69 维（29 本体 + 40 手部）关节实际/目标 + 浮动基座位姿，输出到 `pico2g1/recordings/`（决策记录：留原地，与 `data/` 输入形成对仗，不动共享层默认值）。
- **三状态**（`scripts/04_validate_recording.py` 同款判定）：顶层 `data/+videos/+meta/` 齐全 = 完成；`raw/ + .export/`（缺 meta）= 导出中断可恢复；仅 `raw/` = 未导出。停止录制后后台渲染导出，`meta/info.json` 最后写——所以「meta 缺失」就是中断指纹。
- **校验/诊断**：`scripts/04`（g1_ik/.venv 运行，依赖 pyarrow + 系统 ffprobe）完成态 18 项基线；`--deep` 可借 lerobot 库深加载（本机 cosmos env 的 lerobot 0.4.4 只认 v3.0，v2.1 训练前需转换或用 lerobot ≤ 0.3.x）。
- **恢复**：`MUJOCO_GL=egl python -m sim_scenes.lerobot_recording <录制目录>` 离线续导出，幂等可重试。**实测**（2026-10-20）：录制 `g1_20261020_181011_a63011` 实跑产出、导出被中断，数据本体（raw）完好且 04 可诊断；该产物 2026-10-21 核实已清理（录制链路可复录，重录后如再遇中断按本节恢复）。
