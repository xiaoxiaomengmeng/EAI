## ① 启动配置总览 dump（L1-L128）—— "参数审计"

### 这块长什么样

```python
# L1-128，一次性打印一个大 dict，分 3 个子结构：
{
    'env':    {...},   # 仿真环境配置（相机、观测空间、fps、task...）
    'eval':   {...},   # 评估超参数（batch、轮数、录视频、async envs...）
    'policy': {...},   # PI05 policy 完整配置（架构、归一化、LoRA / expert 开关...）
    'rename_map': {},  # 数据集键名映射（LIBERO 不需要，为空）
    'seed': 1000,      # 评估种子（固定 1000，可复现）
    'trust_remote_code': False
}
```

### 怎么看 —— 3 个子 dict 分别盯哪些键

#### 1.1 env{} 子 dict（重点盯 6 个键）

| 键 | 日志里的值 | 注释 / 正常值 / 异常 |
|----|-----------|---------------------|
| `camera_name` | `'agentview_image,robot0_eye_in_hand_image'` | **2 个相机**（主视角 + 右腕视角）。pi05 期望 3 个相机槽位，policy 配了 `empty_cameras=1` 补空槽 → ✅ 一致 |
| `fps` | `20` | LIBERO 标准 10Hz 采集 × 2x interpolation 到 20 fps。正常。如果是 ALOHA 这里应该是 50 |
| `task` | `'libero_spatial'` | 跑的是 Spatial 10 个空间理解任务。正常。其他值：`libero_object` / `libero_goal` / `libero_10` |
| `observation_height/width` | `360 / 360` | env 原始出图 360×360。policy 里会 resize 到 256×256（见 policy.image_resolution）。正常 |
| `features_map.pixels/*` | `'observation.images.image'` 和 `'observation.images.image2'` | env 的像素键名 → lerobot 标准键名的映射。pi05 policy 需要的是 `observation.images.image` 和 `observation.images.image2`，匹配了。**如果这里配错，会报 KeyError 或 shape mismatch** |
| `features.action.shape` | `(7,)` | 7D 动作（6 关节位姿 + 1 夹爪开合）。LIBERO 是单臂，ALOHA 是 14D。正常 |

**出问题的信号**：
- `camera_name` 只有 1 个 → 相机没配全，pi05 双腕能力浪费
- `fps=50` → 跑错了 ALOHA 环境，不是 LIBERO
- `features.action.shape=(14,)` → 配成了 ALOHA 双臂
- `task=aloha_sim_transfer_cube_human` → 配错环境了

#### 1.2 eval{} 子 dict（重点盯 4 个键）

| 键 | 日志里的值 | 注释 |
|----|-----------|------|
| `n_episodes` | `1` | **每个 task 跑几轮**。注意：是"每个 task"，不是"总共几轮"。LIBERO Spatial 有 10 task → 总共跑 10 集 |
| `batch_size` | `1` | 同时跑几个并行 env。5090 32GB 开 batch 1 是合理的（env 很占 CPU 内存） |
| `recording` | `False` | 这里是 lerobot 的 push_to_hub 录视频开关，**不是本地录视频**！本地 mp4 无论如何都会存（见下文） |
| `use_async_envs` | `True` | 用 SubprocVectorEnv 多进程异步跑 env。正常（比 Sync 快，但调试 traceback 麻烦） |

**出问题的信号**：
- `n_episodes=0` → 没跑任何数据
- `use_async_envs=False` → 慢，但调试方便
- `recording=True` + `recording_repo_id=None` → 会尝试上传视频，没配 wandb/hf 会报错

#### 1.3 policy{} 子 dict（重点盯 10 个键，最核心）

| 键 | 日志里的值 | 注释 / 正常值 / 异常 |
|----|-----------|---------------------|
| `type`（隐含，在 checkpoint config.json 里） | **pi05** | 必须是 pi05！如果是 pi0 说明 checkpoint 选错了。验证方法：看是否有 `action_expert_variant` 这个键（pi0 没有） |
| `action_expert_variant` | `'gemma_300m'` | Expert 是 300M Gemma。正常 |
| `paligemma_variant` | `'gemma_2b'` | PaliGemma 2B 骨干。正常 |
| `pretrained_path` | `'outputs/pi05_libero_lora/checkpoints/last/pretrained_model'` | **加载的 checkpoint 路径**。必须指向你训练出来的那个路径。如果这里错了 → 评估的不是你想评的模型 |
| `use_peft` | `True` | 正在用 LoRA 微调权重。如果是 Expert 模式训练出来的 checkpoint，这里应该是 `False` |
| `train_expert_only` | `False` | LoRA 模式下不冻结 Expert。Expert 模式下应为 `True` |
| `empty_cameras` | `1` | **关键**：补 1 个空相机槽位。LIBERO 2 相机 + 1 空槽 = 3 相机，正好填满 pi05_base 的 3 个相机输入。**如果这里是 0 → 2 相机 vs 3 期望，shape 不匹配 OOM 报错**；如果是 2 → 浪费 1 个空槽，没利用 LIBERO 双相机优势 |
| `normalization_mapping` | `{'ACTION':'MEAN_STD','STATE':'MEAN_STD','VISUAL':'IDENTITY'}` | **关键**：ACTION/STATE 用 MEAN_STD（因为 LIBERO 数据集无 q01/q99 quantile），VISUAL 用 IDENTITY（像素 0-255 不做统计归一，模型自带预处理）。**如果 ACTION 是 QUANTILES → 加载 stats 时报 KeyError** |
| `n_action_steps` | `10` | pi05 一次预测 10 步动作 chunk。pi05 官方默认就是 10。pi0 默认是 50 |
| `dtype` | `'bfloat16'` | bf16 推理。正常。如果是 float32 → 显存翻倍，慢但精度高 |
| `device` | `'cuda'` | GPU 推理。如果是 'cpu' → 慢到没法用，查 CUDA 装对了没 |
| `input_features` | 3 个相机键 + 1 个 state 键 共 4 个 | `observation.images.image` + `image2` + `empty_camera_0` + `observation.state`。**正常：正好 3 相机 + 1 state** |
| `output_features.action.shape` | `(7,)` | 7D 动作，与 env.action.shape 必须一致。✅ |
| `image_resolution` | `(224, 224)` | 喂给 SigLIP ViT 的图像大小。env 出 360→policy resize 到 224。正常 |

**出问题的信号（评估失败 Top 5 根因都在这儿）**：
1. `empty_cameras` 不是 1 → shape mismatch 或相机浪费
2. `normalization_mapping.ACTION=QUANTILES` → `KeyError: 'q01'` 直接崩
3. `pretrained_path` 指错目录 → 要么加载不了权重，要么评估错模型
4. `use_peft=True` 但 checkpoint 是 Expert 模式的 → adapter 加载失败 warning
5. `device='cpu'` → 慢到你以为卡死了

### 这块的意义

**这块是"启动审计"**。很多时候评估结果不对，不是 rollout 阶段出问题，而是**参数没传对**。建议每次跑完第一步就扫一遍上面的 10 个 policy 关键键，确认：empty_cameras=1 ✅、normalization_mapping 是 MEAN_STD ✅、pretrained_path 正确 ✅、device=cuda ✅、n_action_steps=10 ✅。

### 怎么看 —— 5 行逐行解读

| 行 | 含义 | 正常值 |
|----|------|--------|
| 第 1-3 行 PI05 声明 | lerobot 的 PI05 是从 openpi 官方 JAX 版直接 port 来的 PyTorch 实现，兼容 API | 必须有，说明加载的是 pi05 policy |
| `Loading model from: models/pi05_libero_base` | **实际加载的基座路径**。因为 checkpoint 是 LoRA 版的（只存 adapter），权重文件里不包含完整基座 safetensors，所以要从 `pretrained_path` 对应的基座路径 fallback 加载 | ✅ 这里是 pi05_libero_base 才对。如果跑 aloha_static 应该是 pi05_base。要对标官方 benchmark 必须是 pi05_libero_base |
| `✓ Loaded state dict from model.safetensors` | 基座 safetensors 读出来了 | ✅ |
| `Remapped 812 state dict keys` | lerobot 的 state_dict key（带 `paligemma_with_expert.` 前缀）和 safetensors 的 key 做了一次重映射 | **812 个 key 是 pi05 的标配**。如果数字比 812 小很多（比如 <500），说明加载了 pi0 的权重或者文件损坏 |
| `All keys loaded successfully!` | 所有 state dict key 都匹配上了，没有 missing / unexpected keys。这是模型加载的金标准 | ✅ 必须看到这一行。如果有 missing keys / unexpected keys，会在这一行之前打印 warning 列表，并且 loss 会一开始就 Nan |

**失败信号**：
- 812 数字不对（比如 780 / 820 等）→ 基座错了，checkpoint 对应基座应该是 pi05_libero_base，别写成 pi05_base
- 看到 `Unexpected key(s) in state_dict` → checkpoint 和 policy 版本不兼容（lerobot v0.6 vs v0.7 改了 key 命名）
- `Missing key(s) in state_dict` → 同上
- 最后一行没有 `All keys loaded successfully!` → 权重部分加载，rollout 输出的动作会随机或 NaN

## ⑤ Rollout 进度条（L161-L1929 前半）—— "最占篇幅但信息量最大"

这一块占了日志 **~1800 行（90% 篇幅）**，但都是 tqdm 进度条反复刷的输出。

### 5.1 进度条的结构（两层 tqdm）

```
外层：Stepping through eval batches: 100%|█| 1/1 [00:06<00:00,  6.90s/it, running_success_rate=100.0%]
          ↑ 外层遍历 task。10 个 task × n_episodes=1 → 总共 "1/1"（每个 task 一个 episode）
          ↑ s/it：每个 task（含 episode 内所有 step）的总耗时
          ↑ running_success_rate：截止到当前 task 的平均成功率

内层：Running rollout with at most 280 steps: 100%|█| 280/280 [00:06<00:00, 46.67it/s, running_success_rate=100.0%]
          ↑ 每个 episode 内的 step 执行。LIBERO env 默认最多 280 步 = 14 秒 @ 20 fps
          ↑ 280/280：跑满了 280 步（失败或接近超时）。如果 280 之前任务完成，会显示 "X/280"（提前终止，比如 200/280）
          ↑ it/s：step 执行速度（每秒多少 step）。正常值：15-50 it/s。如果 <5 it/s 说明慢
          ↑ running_success_rate：到当前 step 为止任务是否已成功（通常前 200 步都是 0.0%，最后几十步跳成 100.0%）
```

### 5.2 10 个 task 的耗时 + 成功率对比表（实测）

| task_id | 外层 s/it | 内层 it/s | 提前终止？ | running_success_rate | 结果 | 备注 |
|---------|-----------|-----------|-----------|---------------------|------|------|
| 0 | 6.90s | 46.67 it/s | ✅（没到 280 步） | 100.0% | ✅ 成功 | 最快之一 |
| 1 | 8.15s | 34.4 it/s | ✅ | 100.0% | ✅ 成功 | 中速 |

### 5.3 从进度条读"深度信息"的技巧

#### A. 看 s/it 判断任务难度

- s/it < 7s → 简单任务（task 2/3/5/0 这种），模型很擅长
- 7s < s/it < 10s → 中等难度（task 1/4/6/7）
- 10s < s/it < 14s → 较难任务（task 8 压线完成）
- s/it > 14s + 跑满 280 步 → 失败或极难（task 9 16.92s → 超时未达 BDDL 成功条件）

#### B. 看内层 it/s 判断 env + model 推理效率

- 40-55 it/s → 极快（模型推理 + env step 均衡）
- 20-40 it/s → 正常
- 10-20 it/s → 偏慢，可能：模型推理慢、env 大、或者 task 本身每步要做多次碰撞检测
- < 10 it/s → 慢了！要么 device=cpu，要么 CUDA OOM fallback，要么 MuJoCo 模型有高复杂度 mesh

#### C. 提前终止（step < 280）代表什么

LIBERO 的 env.step() 返回的 `done=True` 有 3 种情况：
1. **成功终止**：BDDL 目标 predicate 为真（比如 "锅在 stove 上"），env.set_done(True)。内层 step 会提前终止。running_success_rate 会从 0.0% → 100.0%
2. **失败终止**：280 步到了但 BDDL 没成功。running_success_rate 保持 0.0%
3. **碰撞 / 关节超限终止**：robosuite 安全终止

task_id=9 是**跑满 280 步 + running_success_rate=0.0%** = BDDL 目标没达成。要分析到底为啥失败，看视频：

```bash
mpv outputs/eval_pi05_libero_libero_spatial_lora/videos/libero_spatial_9/eval_episode_0.mp4
```

#### D. 内层进度条为什么有重复行？（比如 L163-164 都是 "1/280"）

tqdm 在非交互终端（pipe / redirect 到 log 文件）下每次 refresh 都新打一行，不做 overwrite。所以 1/280、1/280、2/280、3/280、3/280 是正常的——重复行是 tqdm 的 "写入" 和 "重绘刷新" 两条分开的写，实际 step 是对的。**不影响数据，只是日志变多。**

可以用：
```bash
# 只看最后一个 "Stepping through eval batches: 100%" 行（每个 task 1 行）
grep "Stepping through eval batches: 100%" logs/eval_pi05_libero_libero_spatial_lora_20260828_213041.log | tail -10
```

直接得到 10 个 task 的 s/it + running_success_rate，比翻 1800 行省时间。

### 5.4 出问题的信号

- 外层 s/it 突然 > 30s → env 挂了（egl context lost 或 subprocess 卡住）。看是否出现 "Child process terminated" traceback
- 内层 it/s 从 40 骤降到 3 → 模型推理崩了，可能权重加载 partial 或 dtype fallback 到 float32 吃满显存
- 跑了 20+ 个 task 还没结束 → task 数量错了（LIBERO Object 是 20 tasks，Goal 是 10 tasks，LIBERO-10 是 10 tasks）
- running_success_rate 永远 0.0% 即使 s/it < 5s → env 的 reward 函数配置坏了（或 BDDL 文件损坏）。看 per_task 里的 'successes' 字段确认

### 8 个字段逐字段讲解

| 字段 | 值 | 含义 + 怎么理解 | 对官方 benchmark |
|------|----|----------------|------------------|
| **`pc_success`** | **90.0** | **Percentage of Successful episodes：成功率**（成功数 ÷ 总 episode 数 × 100）。**这是评估最核心的指标，就看它** | 官方 LeRobot π0.5 Spatial 是 **97.0%**。我们 90%，差距 7%。**非常不错的首次结果** |
| `avg_sum_reward` | 0.9 | 每个 episode 的 reward 总和（所有 step 的 reward 加起来）取平均。LIBERO 成功 episode 通常 sum_reward=1.0、失败=0.0，所以 avg_sum_reward ≈ pc_success/100 | 90% ≈ 0.9 完全一致 |
| `avg_max_reward` | 0.9 | 每个 episode 最大 reward（max over steps）取平均。LIBERO 是"成功=1 失败=0"二元 reward，所以 avg_max_reward == avg_sum_reward | ✅ 一致，说明 reward 函数是二元的 |
| `n_episodes` | 10 | **实际跑了多少集**（= n_tasks × N_EPISODES）。这里是 10 tasks × 1 ep = 10。**正式 benchmark 应该是 10 × 50 = 500 episodes** | ✅ 10 集 smoke test，足够定性 |
| `eval_s` | 97.54 | 整个评估命令的总耗时（秒）。1 分 37.5 秒 | 正式 50 集 / task 约 500 episodes × 9.75s ≈ 81 分钟 |
| `eval_ep_s` | 9.75 | 平均每个 episode 耗时（eval_s ÷ n_episodes）。正常值 8-15 秒 | 9.75s/ep 合理 |
| `video_paths` | 10 条绝对路径 | 每个 episode 的视频路径。**无论 eval.recording 设没设，本地 mp4 都存了**！10 个 task × 1 集 = 10 个 mp4 | 调试失败原因：直接打开 task_id=9 看 |
| `predicted_video_paths` | 空 | 预测视频（仅 diffusion 类 policy 用，PI05 action chunk 不输出），忽略 | - |

### 关于 pc_success 90% 的深度解读

10 个任务里失败 1 个（task_id=9），所以 9/10=90%：

```
pc_success = (successes.count(True) / len(successes)) * 100
           = (9 True / 10 total) * 100
           = 90.0%
```

官方 π0.5 LIBERO Spatial 97% 来自 **500 集 485 成功**（50/task × 97% = 48.5 / task）。我们只跑了 10 集（每个 task 1 集），统计波动大。典型情况：task_id=9 在 50 集中可能 48 集成功（96%）+ 2 集失败，那总成功率就是 (9×1.0 + 0.96)/10 = 99.6% per_episode 均值（接近官方）。**想得到统计稳定的结果，必须 N_EPISODES ≥ 20（通常 50）。**

### 出问题的信号

| 现象 | 含义 | 怎么办 |
|------|------|--------|
| pc_success = 0.0 | 所有 episode 全失败 | 看 per_task successes 字段，是不是 reward 函数坏了或模型权重加载 partial |
| n_episodes < N_EPISODES × n_tasks | 有 task 提前 crash | 看前面有没有 traceback，是否 SubprocVectorEnv 子进程死 |
| video_paths 长度 < n_episodes | 视频有几个没存 | 看 mp4 文件路径是否可写（权限 / 磁盘满） |
| avg_sum_reward 远离 pc_success/100 | reward 不是二元的（比如 LIBERO-10 有 dense reward） | 正常，看任务定义 |
