## 第一部分：场景搭建（env.reset() 里发生了什么）

> 读日志对应：[22 号文档阶段 ③"10 个 vec env built"](./22-PI0.5-LIBERO评估日志全链路解析-v1.0.md#L138-L154) — 日志里每行 `Built vec env | task_id=N | n_envs=1` 就是这一套流程执行成功的信号。

### 1.1 三层架构：从"布景"到"剧本"到"具体演员站位"

LIBERO 的场景不是"一个 XML 文件说了算"，而是三层叠加，每层的职责和灵活性严格解耦：

```
Layer 1：场景 XML（= 布景，所有人共用）
    ↓ 指定用哪个桌子、哪个机器人、哪个相机
Layer 2：BDDL task 定义（= 剧本 + 演员表）
    ↓ 指定这一集要放哪些物体、goal 是什么逻辑
Layer 3：init_state pickle（= 具体演员站位）
    ↓ 指定本次 episode 机器人具体关节角度、物体具体坐标
```

下面逐层详解。

---

### 1.2 Layer 1：场景 XML `libero_tabletop_base_style.xml` —— 静态场景骨架

**路径**（assets 安装后实际位置）：

```
~/.libero/assets/scenes/libero_tabletop_base_style.xml
软链 → .venv312/site-packages/libero/libero/assets/scenes/libero_tabletop_base_style.xml
```

**作用**：定义**所有 40 个 LIBERO tasks 共享不变的静态世界**。就像话剧的舞台：桌椅位置、灯光、摄像机不动，只换演员和台词。

**XML 里包含什么**（MuJoCo MJCF 格式）：

| 区块 | 说明 | 关键参数示例 |
|------|------|-------------|
| `option` | 物理引擎配置 | gravity=(0,0,-9.81)、integrator=Euler、timestep=0.0025（2.5ms） |
| `visual` / `quality` | 渲染质量 | shadows=False（离屏 benchmark 不需要，省 GPU 时间） |
| `worldbody` 下 `light` | 灯光 | 2-3 盏方向光 + 环境光 |
| `worldbody` 下 `camera` × 2 | 2 个相机 pose | ① `agentview` 第三方主视角（fov 45°，高度 80cm 俯拍桌面）② `robot0_eye_in_hand` 腕视角（装在 Panda 末端，fov 60°） |
| `worldbody` 下 `floor` / `table` | 地面 + 桌面 | 桌面尺寸 1.2m × 1.5m，高度 0.85m，木纹纹理 |
| `include panda_arm.urdf` | 机器人 URDF 引用 | Panda Franka Emika 7DoF 机械臂 + 二指夹爪，底座在桌面中心后方 10cm |
| `actuator` | 关节驱动器配置 | 7 关节 torque actuator + 夹爪 position actuator（libero control_mode=relative 默认通过 OSC 关节 torque 实现） |

**为什么 XML 里不包含任务物体？** 这就是解耦设计：场景 XML 只放"永远不变"的桌子/机器人/相机，任务物体（锅、盘子、杯子、炉子、橱柜、抽屉）留给 Layer 2 BDDL 指定——这样改任务不用改 XML，改 BDDL 就行。

### 1.3 Layer 2：BDDL（Behavior Domain Description Language）—— 任务语义

每个 LIBERO task 对应一个 `.bddl` 文本文件，位置：

```
.venv312/site-packages/libero/libero/bddl_files/
├── libero_spatial/        # 10 个空间任务：on/in/under/next_to 等空间关系
│   ├── TASK_spatial_0.bddl
│   ├── TASK_spatial_1.bddl
│   └── ...
├── libero_object/         # 20 个物体操作任务：抓+放复杂物体组合
├── libero_goal/           # 10 个目标条件任务：多步 BDDL goal
└── libero_10/             # 10 个最复杂任务（多物体+多子目标组合，520 步上限）
```

#### 1.3.1 BDDL 文件结构（以一个 Spatial task 为例）

```lisp
; TASK_spatial_0.bddl （"把杯子放到托盘上"任务的 BDDL 文本定义）

(define (problem libero-spatial-0-task)
  (:domain libero_tabletop_manipulation)   ; 所属领域（含 on/in/under 等谓词定义）

  ; ----- 物体类型声明 -----
  (:objects
    cup_0        - mug                    ; 一个马克杯（mug 类型继承 object）
    tray_0       - tray                   ; 一个托盘（tray 类型）
    robot0       - panda_7joint           ; Panda 机器人
    robot0_left_finger robot0_right_finger - finger   ; 左右夹爪
    table_center table_right - table_region           ; 桌面两个区域（空间锚点）
  )

  ; ----- 初始态 init：episode 开始时必须满足的谓词 -----
  (:init
    (on cup_0 table_center)               ; 杯子必须在"桌子中央区"
    (on tray_0 table_right)               ; 托盘必须在"桌子右区"
    (in-region cup_0 reachable_workspace) ; 杯子必须在机器人可达工作空间内
    (in-region tray_0 reachable_workspace); 托盘也在可达范围
    (in-gripper empty robot0)             ; 夹爪初始是空的
    (stationary cup_0)                    ; 杯子初始静止（防止从运动态开始）
  )

  ; ----- 目标态 goal：episode 成功必须满足的谓词 -----
  (:goal (and
    (on cup_0 tray_0)                     ; 核心目标：杯子 ON 托盘上
    (in-gripper empty robot0)             ; 附加约束：放下后夹爪必须空
    (stationary cup_0)                    ; 杯子最后要静止（不能还在滑动就算成功）
    (stationary tray_0)                   ; 托盘也要静止
  ))
)
```

#### 1.3.2 BDDL 的两个核心机制

| 机制 | 实现源码位置 | 怎么工作 |
|------|-------------|---------|
| **物体注入**（从 BDDL 物体列表到 MuJoCo 场景） | `bddl_base_domain.py:L311 _populate_assets_from_bddl()` | 遍历 `(:objects ...)` 里的物体，根据类型加载对应 MJCF（`cup_0` 是 mug → 加载 mug.xml；`tray_0` 是 tray → 加载 tray.xml），然后按 `(:init ...)` 里的 `(on cup_0 table_center)` 初始 region 约束把物体大致放到指定区域（随机采样位置，在 region 内均匀分布）。这些 MJCF 模型文件就是 **lerobot/libero-assets 里的 objects/ 下 587 文件的一部分**。最后把物体 MJCF 合入主场景 XML（Layer 1 的 table+robot），用 `ET.parse` + `reset_from_xml_string` 重建 MuJoCo `mjModel` |
| **success 判定**（goal 谓词 true/false 检查） | `bddl_base_domain.py:_check_success` + `CheckSuccess` 类 | 每个 timestep 调用 `check_success(mjData)`。先把机器人状态翻译成谓词：算 cup_0 的 COM 坐标和 tray_0 的 AABB 盒子，如果 cup_0.z_top > tray_0.z_bottom 且 cup_0 的 xy 在 tray_0 xy 内 → `(on cup_0 tray_0)` = True。所有 goal 谓词 AND 起来全 True → success=True，episode 提前终止，reward=1.0 |

**BDDL 对"控制变量"的最大贡献**：成功判定写在**可阅读的文本文件**里，随 `hf-libero` 包分发，所有评测者同一版本下逻辑字节一致——不会出现"你 env 的 reward 函数改过，我 env 没改，结果不可比"的问题。

#### 1.3.3 40 个 BDDL task 的 difficulty 梯度（对应你日志里 task_id=9 为什么失败）

| 子集 | 任务数 | goal 典型谓词 | max_steps | 难点 | 你 smoke test 成功率 |
|------|--------|---------------|-----------|------|---------------------|
| libero_spatial | 10 | `on(x, y)`, `in(x, y)`（单物体单一空间关系） | 280 | task_id 低：摆得近，容易；task_id=8/9：放抽屉里 / 精准对齐，需要精细位姿 | 90%（9/10，task_id=9 超时） |
| libero_object | 20 | `opened(door)`, `stacked(x,y,z)`（物体几何属性、堆叠） | 280 | 20 个任务更密，需要开抽屉 / 堆叠 2-3 个物体 | ⏳ |
| libero_goal | 10 | 多个 goal 子目标 AND：`on(a,b) ∧ in(c,d) ∧ closed(drawer1)`（多目标联合） | 300 | 多步规划，完成 A 才能去 B，子目标之间相互影响 | ⏳ |
| libero_10 | 10 | 最难组合：长时序 + 多物体 + 精细姿态（典型 LIBERO benchmark 用） | 520 | 比如"拿纸巾擦桌子，把擦过的纸巾丢垃圾桶，把垃圾桶盖盖上"，需要 4-5 个子动作 | ⏳ |

task_id=9 失败的常见 BDDL 原因（推测空间任务 id=9 是类似 `in(cup, drawer_bottom)` 这种放进抽屉任务）：
1. `in(cup, drawer_bottom)` 需要杯子**完全落入**抽屉内部 AABB（不是 99% 进去就算）
2. 附加 `stationary(cup) ∧ closed(drawer)`（夹爪必须退后还关上抽屉）
3. 280 步时间紧，放杯子 + 关抽屉需要 ~3 个动作序列，LoRA 200 步 checkpoint 精度不足以在时限内完成

### 1.4 Layer 3：init_state pickles —— 具体演员站位（保证可解 + 可复现）

Layer 2 BDDL 的 `(:init ...)` 定义了物体必须在"桌子中央区域"这种**软约束**。软约束下如果直接随机采样，可能产生"杯子离机器人太远 / 物体在奇异位附近 / 夹爪刚好卡住杯子把手"这种情形——BDDL 说"可达"，但实际机器人做不到。LIBERO benchmark 用 init_state pickle 彻底解决了这个问题。

#### 1.4.1 init_state 是什么

路径：`.venv312/site-packages/libero/libero/init_files/`，每个 task 一个 `.pkl`。pickle 里是一个 list，长度 = 该 task 可用的初始态变体数（通常 100-500 个变体）：

```python
# 每个元素是一个 init_state dict，人类专家 + 算法后处理验证过：
{
    'sim_state': np.ndarray,      # MuJoCo 扁平 state 向量（mjData.qpos + qvel + act 拼接）
                                   # → 可以直接 sim.set_state_from_flattened()，跳过 BDDL 初始化
    'task_descriptions': str,     # "Put the cup into the bottom drawer"（自然语言 task 描述）
    'success_trajectory_ref': ... # 可选：人类专家的成功轨迹，用于 debug
}
```

#### 1.4.2 env.reset() 路径差异（init_states=True vs False）

```python
# libero/libero/envs/bddl_base_domain.py reset() 伪代码：
def reset(self, seed=None, options=None):
    if self.init_states and self._init_state_pool:
        # ===== init_states=True（benchmark 用，评估脚本默认）=====
        # 不按 BDDL init 随机采样摆物体，直接从 pickle 里选 1 个"已验证成功"的初始态：
        rng = np.random.default_rng(seed)
        chosen = rng.choice(self._init_state_pool)   # ★ seed=1000 → 选的永远是同一个 variant
        sim.set_state_from_flattened(chosen['sim_state'])  # 直接覆盖 MuJoCo state
        sim.forward()                                 # 计算接触 / 速度
    else:
        # ===== init_states=False（调试/训练用）=====
        # 1. 按 BDDL (:objects) 注入 XML 物体
        mujoco_arena = self._populate_assets_from_bddl(
            TableArena(xml_path_completion("libero_tabletop_base_style.xml")))
        # 2. 按 BDDL (:init ...) 区域约束随机采样物体位置
        for obj, region in init_regions.items():
            obj.set_pose(
                pos=uniform_sample_in_AABB(region.AABB),
                quat=random_rot_z()
            )
        # 3. reset_from_xml_string 重建 MuJoCo model → 初始化
        self.sim = MjSim(xml_string_to_mjcf_model(mujoco_arena.get_xml()))

    return self._get_observation()    # 输出 2 张相机渲染图 + 8D state
```

#### 1.4.3 init_state 的"控制变量"意义 —— 为什么 benchmark 强制 True

| 对比维度 | init_states=True（benchmark） | init_states=False（随机） |
|---------|-------------------------------|--------------------------|
| **task 可解性** | 100%（每个初始态都验证过） | 可能出现不可解的初始态（概率 ~5-20%） |
| **可复现性** | seed=1000 × pickle 文件哈希固定 → 你我他跑同一 task_id 得到完全相同的机器人关节角 + 物体坐标 | seed=1000 也只能保证随机数序列一致，但物体采样算法/版本变动会导致实际位置不同 |
| **成功率含义** | 成功率差 = 纯模型能力差 | 成功率差 = 模型能力 + 采样分布差异 |
| **方差** | N_EPISODES=50 时 pc_success 方差 < 5% | N_EPISODES=50 时方差可达 15%+ |

一句话：**`init_states=True` 把"初始态随机变量"从 benchmark 里去掉了，让 pc_success 只剩一个自变量 —— 你的模型权重。**

### 1.5 其他控制变量手段（benchmark 公平性的 3 个细节）

除了 Layer 1-3 的三层结构，LIBERO 还用另外 3 个机制保证"所有评测者在同一条起跑线上"：

| 手段 | 实现位置 | 作用 |
|------|---------|------|
| **评估 seed=1000（lerobot 默认）** | `bot_eval.py:L741 'seed': 1000` → 传入 env.reset(seed=...) + init_state RNG | init_state pick 的选择顺序（先抽哪个 variant）+ 任何 env 内部随机扰动（物体微小抖动 noise、关节初始化噪声）100% 可复现 |
| **max_steps 硬编码** | `env_wrapper.py OffScreenRenderEnv` 构造：Spatial=280, Object=280, Goal=300, 10=520 | 时间预算固定，模型不能靠"耗时间磨成功" |
| **渲染链硬编码** | 场景 XML 的相机内参/FOV + lerobot 的 resize_with_pad_torch 算法 + IDENTITY + SigLIP [-1,1] 三段 | 视觉输入链路固定，评估者之间像素级输入值一致（除了 GPU rounding 末位差异） |

## 第二部分：推理交互——从场景像素到模型输出动作、再回到物理世界

> 读日志对应：[22 号文档阶段 ⑤ Rollout 进度条](./22-PI0.5-LIBERO评估日志全链路解析-v1.0.md#L161-L1929) — 内层 `Running rollout ... 280 steps` 进度条每推进 1 it，就是这个循环执行了 1 次。

### 2.1 循环结构总览（单 episode 280 次循环）

```python
# lerobot/scripts/lerobot_eval.py rollout() L167-379（伪代码，保留关键注释）
policy.reset()                                               # 清空 action queue + memory queues
observation, info = env.reset(seed=seeds)                    # 第一部分的场景搭建

for step in range(max_steps):                                 # max_steps = 280 for Spatial
    # ▼▼▼ 第二部分：模型输入（本节 2.2 详解）▼▼▼
    observation = preprocess_observation(observation)        # L274：uint8→0-1 + HWC→CHW + numpy→tensor
    observation["task"] = env.call("task_description")       # L281：BDDL goal→自然语言
    observation = env_preprocessor(observation)              # L289：LiberoProcessorStep 键名对齐
    observation = global_preprocessor(observation)           # L291：MEAN_STD（state/action）/ IDENTITY（视觉）

    # ▼▼▼ 第三部分：模型推理（本节 2.3 详解）▼▼▼
    with torch.inference_mode():
        action = policy.select_action(observation)           # L293：★ 核心—— 动作 chunk 缓存 + Flow Matching 推理
    action = postprocessor(action)                           # L296：MEAN_STD 反归一化 → 物理单位
    action_numpy = action.to("cpu").numpy()                  # L303：[1,7] tensor → numpy

    # ▼▼▼ 第四部分：物理推进（本节 2.4 详解）▼▼▼
    observation, reward, terminated, truncated, info = env.step(action_numpy)  # L307：OSC IK → mj_step → 下一帧
    # info["is_success"] → BDDL goal 判定（本节 1.3 的 CheckSuccess 类）
```

### 2.2 模型输入链：从 MuJoCo 像素 → PaliGemma 视觉 tokens（6 步处理）

#### 2.2.1 第 0 步（env 内）：MuJoCo EGL 离屏渲染 → 360² uint8 HWC

```python
# robosuite OffScreenRenderEnv.get_observation()：
# 推进物理后，sim.render() 调 MuJoCo EGL GPU 渲染管线：
#   MuJoCo → shader: 顶点 shader + 片段 shader → framebuffer(EGL pbuffer) → map→CPU
rgb_agentview = sim.render(
    height=360, width=360,
    camera_name="agentview_image",
    mode="offscreen"
)   # → numpy (360, 360, 3) uint8, 值 [0, 255], HWC channels-last

rgb_wrist = sim.render(
    height=360, width=360,
    camera_name="robot0_eye_in_hand_image"
)   # → numpy (360, 360, 3) uint8

# 打包成 lerobot env 输出：
observation = {
    "observation.images.image":  rgb_agentview,   # 360² HWC uint8
    "observation.images.image2": rgb_wrist,       # 360² HWC uint8
    "observation.state": np.concatenate([joint_pos, gripper_qpos]),  # 7+1 = 8D
}
```

#### 2.2.2 第 1 步：preprocess_observation —— 标准化 + HWC→CHW + numpy→tensor

```python
# lerobot_eval.py L274（lerobot 通用）
for k, v in observation.items():
    if "image" in k and isinstance(v, np.ndarray) and v.dtype == np.uint8:
        v = v.astype(np.float32) / 255.0             # [0,255] → [0.0, 1.0]
        if v.ndim == 3 and v.shape[-1] == 3:          # HWC
            v = v.transpose(2, 0, 1)                   # (H,W,3) → (3,H,W) = CHW（PyTorch 要求）
        observation[k] = torch.from_numpy(v)           # numpy → tensor
    elif k == "observation.state":
        observation[k] = torch.from_numpy(v.astype(np.float32))

# 结果（LIBERO 单次 env batch_size=1）：
# observation.images.image  → tensor shape [1, 3, 360, 360]   值域 [0,1]
```

**为什么视觉用 IDENTITY 不用 MEAN_STD？**
- MEAN_STD 是基于**数据集像素统计**的 mean/std（所有数据集 RGB 均值接近 [0.5,0.5,0.5]）
- 但 PaliGemma/SigLIP 预训练时用的是**固定** `×2 - 1` 到 `[-1, 1]` 的归一化（与数据集无关），和数据集统计值归一化在数学上是**两个不同的空间**
- 如果误用 MEAN_STD 处理视觉 → SigLIP embedding 会偏离预训练分布 → 成功率显著下降（实测可能 -20%+ pc_success）

```python
def _preprocess_images(self, batch):
    images = []
    for key in present_img_keys:            # = [image, image2]（真相机 2 张）
        img = batch[key]                     # [1, 3, 360, 360], float32 [0,1]
        img = img.to(self.device)            # CPU → CUDA

        # resize 算法：转 HWC → resize_with_pad_torch（保持 aspect ratio） → 转回 CHW：
        #   env 360² (正方形) → policy 224² (正方形) → 直接 resize，不需要 padding
        #   如果 env 是 480×640 (4:3) → 长边缩到 224，短边 0 值 padding 到 224 (1:1)
        img = to_HWC(img)                     # [1, 360, 360, 3]
        img = resize_with_pad_torch(img, 224, 224)  # [1, 224, 224, 3]

        # ★ SigLIP 要求：值域 [-1, 1]（预训练时就这么做的）
        img = img * 2.0 - 1.0

        img = to_CHW(img)                     # [1, 3, 224, 224]
        images.append(img)

    # ★ 补空相机槽（empty_cameras=1，pi05 期望 3 相机）
    for _ in missing_img_keys:                # = [empty_camera_0]（伪相机 1 张）
        # 全 -1 的图（对应 SigLIP [-1,1] 中的"最小可能值"，即黑→更黑）
        img = torch.ones_like(last_image) * -1      # [1, 3, 224, 224]，全 -1
        # mask = False → Transformer attention 时这张图所有位置跳过
        mask = torch.zeros_like(last_mask, dtype=torch.bool)
        images.append(img)
        img_masks.append(mask)

    return images, img_masks
    # images:    3 个 [1, 3, 224, 224] 图，值 [-1, 1]
    # img_masks: 3 个 [1] bool → [True, True, False]（第 3 张空图 mask 全 False）
```

### 2.3 动作输出链：Flow Matching 积分 + Action Chunking 缓存

模型推理的调用点只有一个：`policy.select_action(observation)`（L293）。但它内部做了两件聪明事：

#### 2.3.1 Action Queue + Action Chunking（每 10 step 才真正推理 1 次）

```python
# modeling_pi05.py L1174-1191
@torch.no_grad()
def select_action(self, batch):
    self.eval()
    # (memory inference queues if enabled 省略)

    # ★ 核心：Action Queue（episode 开始 policy.reset 清空）
    if len(self._action_queue) == 0:       # 队列空 → 必须推理一次
        # 真正的 Flow Matching 推理（贵）
        chunk = self.predict_action_chunk(batch)   # [1, 50, 7]（50 步 chunk）
        # 只取前 n_action_steps=10 步
        actions_10 = chunk[:, :10, :]              # [1, 10, 7]
        # 存到队列
        self._action_queue.extend(actions_10.transpose(0, 1))
        # queue: deque([ [1,7] step0, [1,7] step1, ..., [1,7] step9 ])

    return self._action_queue.popleft()     # 弹 step0，队列还剩 [step1..step9]
```

**推理频率对比**（以 task_id=5 为例，成功 episode 约 117 step 结束）：

| 模式 | 推理次数（Flow Matching × 10 小步积分） | 加速比 |
|------|------------------------------|--------|
| 每步推理（无 chunk） | ~117 次 | 1× |
| **PI05 chunk=10（默认）** | **~12 次**（ceil(117/10)） | **10×** |

这就是为什么你日志里 `46.67 it/s` 看起来"推理 + 仿真一起只花 21ms/step"——因为 10 步里 9 步是纯弹队列（CPU 操作 0.5ms），只有 1 步是真推理（~200ms），平均到每步 = (200ms + 9×0.5ms + 10×物理 5ms) / 10 ≈ 25ms（40 it/s 量级）。

#### 2.3.2 predict_action_chunk 内部：Flow Matching 10 步积分 → 50×7 动作

```python
# modeling_pi05.py L1193-1222
@torch.no_grad()
def predict_action_chunk(self, batch, **kwargs):
    # 1) 准备输入（上一节 2.2 已经讲过的预处理）
    images, img_masks = self._preprocess_images(batch)    # 3 张 224² [-1,1]
    states, state_masks = self._prepare_memory_states(batch)  # state 8D → pad 32D, mask
    tokens = batch["observation.language_tokens"]          # [1, 200]
    masks  = batch["observation.language_attention_mask"]  # [1, 200]

    # 2) ★ 核心：model.sample_actions() —— Flow Matching 采样
    # PI05 的 PaliGemma+Expert 双模型把输入 -> 一个速度场模型 v(s, x_t, t)
    # Flow Matching 过程：
    noise_actions = torch.randn(1, 50, 7)          # ① 纯高斯噪声初始化动作 chunk
    current = noise_actions
    dt = 1.0 / self.config.num_inference_steps      # 1/10 = 0.1（10 步 Euler 积分）
    for i in range(10):
        t = i * dt                                   # t=0.0, 0.1, ..., 0.9
        velocity = self.model.forward_denoise(      # ② 模型预测速度场（PaliGemma + Gemma Expert 的一次完整 forward pass）
            current, t, images, img_masks, tokens, masks, states, state_masks
        )  # velocity shape = [1, 50, 7]
        current = current + velocity * dt           # ③ 欧拉积分：往速度方向走 dt
    # 10 步后 current 从"完全噪声"变成"似真 50 步 7D 动作序列"
    actions_50 = current                             # [1, 50, 7]

    # 3) unpad：max_action_dim(32) → actual action_dim(7) 已经是 7，跳过
    return actions_50
```

**动作序列理解**：50 步 chunk ≈ 2.5 秒 @ 20fps（50×0.05s）。PI05 policy 一次预测 2.5 秒的动作，然后只消费前 0.5 秒（10 步）——这是**保守设计**：chunk 内 10 步之后累积误差开始变大，所以每 10 步（0.5 秒）用最新视觉重新推理，丢弃剩余 40 步。如果 n_action_steps=50（像 PI0）就是 2.5 秒才重推理一次，更省 compute，但误差累积更大。

### 2.4 物理推进：env.step → IK 逆解 → MuJoCo mj_step → BDDL success 判定

最后一步：模型吐出的"末端该往哪走"怎么变成机械臂的实际运动？LIBERO robosuite Panda 默认的 control_mode=relative + OSC 控制器。

#### 2.4.1 step 内部伪代码

```python
# lerobot_eval.py L307 → libero OffScreenRenderEnv.step() → robosuite BaseEnv.step()
def step(self, action_7d):
    # ===== 2.4.1a OSC 操作空间控制器 =====
    # 输入：7D "末端期望往哪走" dx/dy/dz/dqx/dqy/dqz/dgripper（相对位移）
    # 输出：7D "每个关节的目标位置"（用于 PID torque 控制）
    q = sim.data.qpos[:7]                               # 当前关节位置 7D
    J = self.controller.get_osc_jacobian(q)              # 7×6 Jacobian J(q)：关节空间→操作空间
    # 伪逆 + 阻尼最小二乘（防止奇异时爆炸）
    dq_desired = np.linalg.pinv(J + λ²·I) @ action_7d[0:6]  # 关节增量 dq = J⁺ · dx
    gripper_target = clip(action_7d[6], -1, 1)          # 夹爪开合位置目标
    joint_torque = self.controller.osc_torque(q, dq_desired)  # 加重力补偿 + 关节限位
    sim.data.ctrl[:7] = joint_torque
    sim.data.ctrl[7] = gripper_target * gripper_motor_gain

    # ===== 2.4.1b MuJoCo mj_step 物理积分（50ms 的子 step × 20）=====
    # timestep 0.0025s × 20 substep = 0.05s（一个 env step = 20Hz）
    for _ in range(20):
        mujoco.mj_step(self.model, self.data)
        # 每子步：执行器力 + 重力 + 碰撞（GJK/EPA 距离算法算杯子和托盘的接触）+ 摩擦
    # → 推进后：qpos/qvel 更新，物体（cup/tray）mocap pos 更新，接触力写入 cfrc_ext

    # ===== 2.4.1c 渲染观测 =====
    obs = self._get_observation()
    #   360² agentview image (360,360,3) uint8 ← MuJoCo EGL render
    #   360² wrist    image (360,360,3) uint8
    #   state 8D = joint_pos 7D + gripper_qpos 1D ← 直接读 sim.data.qpos

    # ===== 2.4.1d BDDL success 判定（一次性 CheckSuccess.call）=====
    done = False
    if self._check_success.check(sim.model, sim.data):   # goal 谓词全 True?
        done = True
        reward = 1.0
        info["is_success"] = True
    elif self.cur_step >= self._max_episode_steps:       # 280 步到了?
        done = True
        reward = 0.0
        info["is_success"] = False
    else:
        reward = 0.0
    self.cur_step += 1

    return obs, reward, done, False, info   # obs 是下一轮循环的"新 observation"
```

#### 2.4.2 关键参数（控制变量细节）

| 参数 | 值 | 含义 |
|------|----|------|
| `max_episode_steps` | 280（Spatial） | 14 秒 × 20Hz = 280 step。LIBERO-10 = 520（26 秒） |
| `mujoco timestep` | 0.0025s（2.5ms） | 每 env step = 20 substep 物理积分 |
| `OSC 阻尼 λ` | 0.03 | OSC 伪逆阻尼，奇异时（碗口朝上 vs 朝下）防止 J⁺ 爆炸 |
| `control_mode` | relative | 动作 = **增量**（相对于当前末端姿态差），不是绝对目标位置 |
| `gripper` range | -1（全关）~ +1（全开） | 夹爪开合占动作 7D 中的 1D |

## 附录 A：一句话总结（3 个核心问题各 1 句）

| 问题 | 一句话答案 |
|------|-----------|
| **场景怎么搭**？ | XML 骨架（桌子+机器人）+ BDDL 任务语义（放什么物体、什么算成功）+ init_state pickle（具体演员站位 + 已验证可解）→ env.reset() 一次性 set_state 进 MuJoCo |

## 附录 B：对比 ALOHA（TransferCube 1 task）与 LIBERO（40 tasks）控制变量差异

| 维度 | ALOHA TransferCube（gym_aloha，17 号文档） | LIBERO 4 subsets（本文） |
|------|------------------------------------------|------------------------|
| 任务数 | 1（TransferCube 双臂递物） | 40（4 subsets × 10/20/10/10） |
| 动作维度 | 14D（双臂 7+7） | 7D（单臂+夹爪） |
| BDDL 语义层 | 无（reward 4 阶梯由 env.py 手写） | ✅ 有（goal 谓词判定，写死在 bddl 文件） |
